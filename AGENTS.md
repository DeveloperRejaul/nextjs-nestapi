# AGENTS.md

Context for AI coding agents working in this repo. Read this before making changes.

## What this is

`nextjs-nestapi` — an npm library that lets Next.js **App Router** API routes be written in
NestJS style: decorator-based controllers (`@Controller`, `@Get`/`@Post`/`@Put`/`@Patch`/
`@Delete`/`@Head`/`@Options`), `@Body(DtoClass)` request validation via `class-validator`,
`@AuthGuard`/`@CurrentUser` route protection, `@Use` middleware, and OpenAPI/Swagger doc
generation from the same decorators. It is **routing + validation + auth guard + docs
only** — deliberately no DI container, no modules, no pipes, and `@AuthGuard` is sugar over
`@Use()` (a `context.user` check), not a pluggable Nest-style guard *class* system or a
resolver hook of its own. Legacy TS decorators (`experimentalDecorators`/
`emitDecoratorMetadata`), no `reflect-metadata`.

Origin: the decorator/validation pattern was ported from a sibling project,
`school-management-system` (`/Users/mac/Desktop/dev/school-management-system`), where it was
already proven in production. When in doubt about "how should X behave," that project is the
reference implementation to check against.

## Commands

- `npm run build` — `rm -rf dist && tsup && chmod +x dist/cli.js`. Two parallel tsup configs
  (library entry + CLI entry) in `tsup.config.ts`; both have `clean:false` (only the npm
  script does the `rm -rf`, to avoid the two configs racing and wiping each other's output).
  The CLI config deliberately has **no** `esbuildOptions.drop` — dropping `console.*` would
  silently kill all CLI output.
- `npm run dev` — `ts-node ./src/index.ts` (source, not built).
- `npm run test` — `npm run build && npm link` (there is no unit test suite; "testing" this
  library means building it, linking/packing it into `example/`, and exercising real routes
  against a real `next dev` server — see "How to verify a change" below).

## Architecture notes

### Parameter decorators and method wrapping (`param-registry.ts`)

SWC/esbuild don't reliably apply parameter-decorator prototype mutations the way `tsc` does,
so parameter decorators (like `@Body`) don't mutate the class directly. Instead:
`registerParam(target, propertyKey, parameterIndex, resolver)` stores a resolver function in
a registry keyed by class+method+index. `@Controller` (via `wireControllerMethods`) reads
that registry — plus `route.ts`'s `routeRegistry` for each method's `@Use()` middleware list
— at class-decoration time, and rewires every route method once to run, in order: the
app-level middleware chain (`utils/global-middleware.ts`), then this method's own `@Use()`
chain, then parameter resolution, then the original method body. This indirection (wrapping
the prototype method itself, not something a router later wraps around) is required for two
reasons — don't "simplify" either away:

1. A parameter decorator that reassigns the prototype directly isn't reliably applied by
   esbuild/SWC (verified) — only a class decorator, run after the class is fully defined, is.
2. It's the only way the middleware chain runs identically whether the method is dispatched
   as a real route (through `app.handle()`) or bound and called directly as a Server Action
   (`controller.create.bind(controller)(payload)`) — the latter never goes through
   `register.ts`'s router-dispatch path at all, so middleware composition can't live there.
   See "Auth guard" below for why this mattered enough to redesign around.

Every method that appears in `routeRegistry` for a class gets wrapped — not just ones with
`@Body`/`@CurrentUser` parameters — because app-level middleware (e.g. an auth resolver) has
to run for a plain undecorated route too.

`wireControllerMethods` builds one `context` object per call and threads it through both the
middleware chain and every parameter resolver: the real `RouteContext` for a route dispatch
(detected via `isRouteContext()`, the duck-type check below), or a fresh, minimal synthetic
object (just enough for a middleware to set `.user` on) for a Server Action call, since
there's no request/params/query to build one from. A middleware setting `context.user` is
what `@CurrentUser()` later reads back off that same object.

`param-registry.ts` also exports `isRouteContext()` — the duck-type check that tells apart
"called as a route handler" (has `request`/`params`/`query` and a `.json()` method) from
"called directly as a Server Action" (anything else). It's shared by `@Body` and
`wireControllerMethods` itself, and used to be defined separately, verbatim, in both
`body.ts` and `current-user.ts`; consolidated here since both already import from this
module. If a third decorator needs the same distinction, import it from here rather than
re-defining it again.

### Body validation, and why it also works as a Server Action (`body.ts`)

`@Body(DtoClass)` duck-types its raw input via `isRouteContext()` (above): if it looks like
a `RouteContext`, it reads the JSON body from the request.
Otherwise it treats the argument itself as the raw payload. This means a
`@Body`-decorated controller method works two ways with **zero extra code**:

1. Normal API route, dispatched by the catch-all route through `createApplication`.
2. Bound directly and exported as a Next.js **Server Action**
   (`export const createX = controller.create.bind(controller)`), called with a plain
   object. Validation runs identically; failures return the same
   `{ success: false, message, errors }` shape instead of throwing.

This dual-mode behavior — "action validation" in the user's own terms — is documented in
README.md ("Server Action validation") and in the docs site
(`docs/core-concepts/dto-validation.md`, same heading). It was verified working via a
direct smoke test against the built `dist/` output (bypass `createApplication` entirely,
call the decorated method with a plain object, confirm the validation-failure shape).

File/`FileList` fields are stripped out before `plainToInstance` runs and reattached
untouched afterward — `class-transformer` otherwise crashes trying to construct a `File`
from scratch via `value.constructor`.

### Auth guard (`decorators/auth-guard.ts`, `decorators/current-user.ts`, `utils/global-middleware.ts`)

Originally ported from `school-management-system`'s `@AuthGuard(['ADMIN'])`/`@CurrentUser()`
as a `configureAuth({ resolveUser })` singleton hook (one resolver, called by both decorators)
— **since redesigned again**, because that version had a real bug: `resolveUser` was only
ever invoked from inside `RouteContext`-shaped param resolvers, so a controller method bound
and called directly as a Server Action (`controller.create.bind(controller)(payload)`) never
triggered it — `@CurrentUser()` silently resolved to `null` on every Server Action call, with
no error. The root cause was architectural: `@Use()`/`@AuthGuard()` middleware only ran
inside `register.ts`'s router-dispatch path (`composeMiddlewares` called from
`registerController`'s handler and `createApplication.ts`'s `handle()`), which a directly
bound method call never goes through at all.

The fix: there is no resolver hook anymore. Auth is just `@Use()` middleware like any other —
an app-level `app.use()` middleware (typically) resolves the caller and sets `context.user`;
`@AuthGuard(roles?)` is `Use((context, next) => {...})` sugar that checks
`context.user`/`.role` and returns `Response.Unauthorized()`/`Response.Forbidden()` instead of
calling `next()`; `@CurrentUser()` just reads `context.user` off the same object, no resolver
call of its own. What makes this actually work for a Server Action call too is that
**middleware composition itself moved** into `decorators/param-registry.ts`'s
`wireControllerMethods()` — the method-wrapping mechanism that already ran identically
regardless of call shape (see "Parameter decorators and method wrapping" above) — instead of
living in `register.ts`'s router-dispatch path. `register.ts` and `createApplication.ts` no
longer call `composeMiddlewares` at all; they just call the (already fully wrapped)
controller method and finalize its result.

The app-level middleware chain itself (`app.use()`) is backed by one process-wide array in
`utils/global-middleware.ts`, not per-`NextJsApp`-instance state — a directly-bound Server
Action call has no reference to any particular `createApplication()` return value to look
middleware up on, so a single global list is the only place both call shapes can reach. See
that file's own comment before changing this; don't reintroduce per-instance isolation
without a plan for how a bound method would still find it.

There's still no bundled JWT/session logic and no database dependency — a consumer's
app-level middleware reads whatever it wants (`next/headers`, a header, a cookie) and decides
`context.user` itself. Because `context.request` doesn't exist for a Server Action call
(there's no request to build a synthetic context from), a middleware meant to work in both
call shapes should prefer `next/headers`' `cookies()`/`headers()` (themselves
AsyncLocalStorage-based in real Next.js, so they resolve correctly in either call shape
without touching `context` at all) over reading `context.request` directly.

Verified end-to-end two ways (see `test/`, both run via `ts-node` against the built `dist/`
output, not `src`, per "How to verify a change" below):
`auth-middleware.route.test.ts` dispatches through `createApplication`'s real
`app.handle(request)` path; `auth-middleware.action.test.ts` binds and calls controller
methods directly, the Server Action way, using a Node `AsyncLocalStorage`-backed fake session
in place of a real Next.js request (mirroring how `next/headers` itself works) since there's
no real Next.js runtime in a plain `ts-node` script. Both assert the same outcomes: no token →
401 (`@AuthGuard`)/`Response.Unauthorized()` shape, wrong role → 403 (per-method `@Use()`
role check), correct role → 200/`Created` with `@CurrentUser()` correctly injecting the
resolved user, and a route with no `@AuthGuard` resolving `@CurrentUser()` to `null` instead
of blocking.

### `Response` helper and HTTP status codes (`utils/Response.ts`)

`Response.XXX()` methods return plain objects carrying a visible `statusCode` field (same
convention NestJS's own exception bodies use) — deliberately **not** `NextResponse`
instances and **not** a hidden/Symbol-keyed status, because the same object also has to work
when returned directly from a bound Server Action (see "Body validation" above), where
there's no HTTP response to attach a status to and only plain serializable data survives.

The response-dispatch sites — `register.ts`'s per-route `handler` and `createApplication.ts`'s
`handle()` — both call `buildRouteResponse(context, result)` (exported from `Response.ts`)
before returning a non-`Response` handler result. That function reads `result.statusCode` (if present and
numeric) into a `ResponseInit`, so `return Response.NotFound()` from a handler produces a
real HTTP 404, not a 200 with an error-shaped body. **Before this existed, every
`Response.XXX()` return was silently served as HTTP 200** (a real bug, caught and fixed when
the method set was expanded). If you add a new `Response.XXX()` method, give it a
`statusCode` field or it will silently serve as 200.

`buildRouteResponse` also special-cases `204`/`205`/`304` (`NO_BODY_STATUSES`): the Fetch
spec's `Response` constructor throws "Invalid response status code" if you attempt a body
on those statuses, so `Response.NoContent()` (204) would crash `NextResponse.json(...)` if
passed through the normal path — caught by the end-to-end route-dispatch smoke test, not by
the build or a unit-level check. **Don't call `context.json(result, init)`/`NextResponse.json`
directly at a dispatch site** — always go through `buildRouteResponse`, or a future no-body
status will reintroduce this crash.

Full method set: `Ok`/`Created`/`NoContent` (2xx), `BadRequest`/`ValidationFailed`/
`Unauthorized`/`Forbidden`/`NotFound`/`Conflict`/`TooManyRequests`/`InternalServerError`
(4xx/5xx), plus the pre-existing `BadPage`/`EmptyPage` pagination shapes. Documented in
README.md ("`Response` helper" under API reference) and
`docs/core-concepts/handler-return-values.md` in the doc site — keep both in sync with the
method list here.

### Swagger UI (`openapi/swagger-ui.ts`)

Swagger UI assets are **not vendored** — `createSwaggerUiHandler()` does
`await import("swagger-ui-dist")` (not `require()`) and serves the consumer's own installed
copy. `import()` instead of `require()` is required for Turbopack compatibility (Turbopack's
static external-package analysis can't see through esbuild's ESM `require()` shim, even with
`serverExternalPackages` configured — this cost real debugging time, don't revert it).
Because `import()` needs type info that untyped `require()` didn't, there's an ambient
declaration at `src/types/swagger-ui-dist.d.ts`.

The served HTML injects `<base href="{pathname-without-trailing-slash}/" />` — without it,
relative asset URLs (`swagger-ui.css` etc.) resolve one level too shallow whenever the
request URL lacks a trailing slash.

### Route matching (`createApplication.ts`'s `matchRoute`)

`handle()` walks `this.routes` once per request and calls `matchRoute()` at most once per
candidate, capturing the winning route's params on the same pass — it used to call
`.find()` to locate the route and then call `matchRoute()` again on the winner to get its
params, running the same segment-split-and-compare work twice for every matched request.
Keep this a single pass if you touch it again.

Pure declaration-order, first-match-wins — no static-vs-dynamic
segment prioritization (same as Express). A literal route colliding with an earlier dynamic
one (e.g. `@Get("/:id")` declared before `@Get("/search")` on the same controller) will
never be reached; `:id` matches first. This surfaced as a real test-authoring mistake while
writing the end-to-end smoke test for this repo (a `/hello/with-mw` route was silently
swallowed by an earlier `/hello/:id`) — not a library bug, but a sharp edge worth remembering
when adding routes to any test/example controller: declare specific/literal paths before
colliding param paths on the same controller.

### Middleware composition (`utils/compose.ts`)

`composeMiddlewares(context, middlewares, execute)` is the one place that reduceRight-wraps
a list of middlewares around a base executor. It's called from exactly one place —
`decorators/param-registry.ts`'s `wireControllerMethods()` — which composes the app-level
`app.use()` chain and a method's own `@Use()`/`@AuthGuard()` chain around that method's
parameter resolution and body, on the method itself (see "Parameter decorators and method
wrapping" and "Auth guard" above for why this moved out of `register.ts`/`createApplication.ts`).
**The base `execute` is still the only thing responsible for turning its own result into a
real response** (via `buildRouteResponse`, not something `composeMiddlewares` does) — this
matters because a middleware can short-circuit by returning a plain object directly (e.g.
`AuthGuard` doing `return Response.Unauthorized()` without calling `next()`) instead of a
finalized `NextResponse`. That plain object bubbles up through the compose chain, out of the
wrapped controller method, and back to `register.ts`'s `handler` / `createApplication.ts`'s
`handle()` — *those* layers' own `instanceof Response` / `buildRouteResponse` check is what
actually finalizes it for a real route call (a Server Action call returns it as-is, unfinalized,
by design — see "Body validation" above). Don't "fix" this by adding a finalize step to
`composeMiddlewares` itself; a middleware doing
`const response = await next(); response.headers.set(...)` (see the CORS/timing examples in
the README) depends on `next()` already resolving to a real `NextResponse` when it comes from
the base executor for a route call, not from `composeMiddlewares` finalizing late.

### Peer dependencies

`class-validator`, `class-transformer`, `class-validator-jsonschema`, `swagger-ui-dist` are
`peerDependencies` with `peerDependenciesMeta.optional: true` (not hard `dependencies`) —
deliberate choice so consumers who only need routing/middleware aren't forced to install
validation/docs tooling they don't use. Keep this split when adding new optional integrations.

### Public API surface (`index.ts`)

The barrel intentionally exports **only** what's documented in README.md's API reference —
no low-level registries/plumbing. `controllerRegistry`, `routeRegistry`, `registerParam`,
`wireControllerMethods`, `apiTagsRegistry`, `apiOperationRegistry`, `apiResponseRegistry`,
`bodyDtoRegistry`, `registerBodyDto` were all trimmed from the barrel in an audit pass — none
of them were used anywhere outside their own module via relative imports, so removing them
from `index.ts` was a pure surface reduction, not a behavior change. `registerGlobalMiddleware`/
`getGlobalMiddlewares` (`utils/global-middleware.ts`) followed the same rule from the start:
never added, since `app.use()` (the public entry point to that state) already covers the one
documented, real reason a consumer would need it. Each module imports what it needs directly
from its sibling file. If you add a new decorator that needs cross-module registry access
(the way `@Body`/`@AuthGuard`/`@CurrentUser` do), wire it via a direct relative import first —
only add something to `index.ts` once there's a real, documented reason for a consumer to
import it. The library isn't published yet (unlisted on npm as of this writing), so barrel
changes are still free; that won't be true after the first release — removing something from
`index.ts` post-publish is a breaking change.

## How to verify a change

There's no unit-test-framework-based suite (no jest/vitest), but there is a small persistent
`test/` directory of `ts-node` smoke tests — run `npm run test:smoke` (builds, then runs
`test/auth-middleware.route.test.ts` and `test/auth-middleware.action.test.ts` against the
built `dist/` output). Extend these, or add siblings alongside them, rather than writing a
throwaway script for anything that's likely to regress again (the auth-middleware redesign in
particular — see "Auth guard" above — is exactly the kind of change a throwaway script would
have let silently regress).

To validate a change end-to-end more broadly:

1. `npm run build`
2. Pack it (`npm pack`) into a content-hash-suffixed tarball filename and install that into
   `example/` — **do not reuse the same tarball filename across installs**; Yarn Classic's
   `file:` dependency cache has repeatedly served stale content for a reused filename even
   after `rm -rf node_modules yarn.lock`. If you hit inexplicable stale-code symptoms after a
   reinstall, suspect `~/Library/Caches/Yarn/v6/npm-<pkg>-<version>-<hash>` before anything
   else.
2b. For a quick isolated check that doesn't need the full example app or a persistent test
    (e.g. a one-off check while debugging), a throwaway `ts-node` script run against
    `./dist/index.js` with `experimentalDecorators` compiler options works and is faster —
    see `test/fixtures.ts` or the "Body validation" verification above for the pattern. Delete
    the scratch file afterward, or promote it into `test/` if it's worth keeping.
3. Run `next dev` (Turbopack) inside `example/` and hit the real routes — this is the only
   way earlier Turbopack-specific bugs (the `swagger-ui-dist` `require()` issue) were caught;
   `tsc`/build success alone does not guarantee Turbopack compatibility.

## Known gotchas (already fixed once, don't reintroduce)

- `tsconfig.json`: `experimentalDecorators`/`emitDecoratorMetadata` must be **inside**
  `compilerOptions`, not siblings of it.
- `tsconfig.json`: `lib` must include `"DOM","DOM.Iterable"` or `FileList`/`Request.json()`
  types break.
- `package.json` `files`/READMEs are case-sensitive on publish — the canonical filename is
  `README.md` (was once `readme.md`, broke on case-sensitive machines).
- CLI's `relativeImport()` path-diffing: diff `dirname(to)` vs `dirname(from)` and reattach
  `basename(to)` separately — don't `path.relative()` the full paths directly when a file and
  a same-named sibling directory (`src/app.ts` vs `src/app/`) are both in play.
- CLI's `generate controller` array-splicing into `controllers: []`: never build the
  replacement via a nested `.replace(innerMatch, newValue)` when `innerMatch` can be an empty
  string — `"".replace("", x)` inserts at position 0 of the *whole* string, not where you
  think. Reconstruct the full matched substring directly instead.
- CLI's `printResults()` (`cli.ts`) only ever receives `"written" | "skipped"` from
  `writeFileSafe()` — a third `"registered"` status it checked for came from a *different*
  return value (`tryRegisterController`'s own result, already handled separately by `main()`)
  and could never actually appear in `results`. Caught in a dead-code audit; don't
  reintroduce a branch for a status `results` items can't carry — check what a function
  actually returns before adding a case for it.
- `Response.NoContent()` (and any future `Response.XXX()` using 204/205/304): the Fetch
  spec's `Response` constructor throws if you attempt a body on these statuses.
  `buildRouteResponse()` (`utils/Response.ts`) special-cases them — go through it, don't call
  `context.json()`/`NextResponse.json()` directly at a dispatch site (see the `Response`
  helper section above; this was a real crash caught by the end-to-end route-dispatch smoke
  test, not by the build).
