Context for AI coding agents working in this repo. Read this before making changes.

## What this is

`nextjs-nestapi` — an npm library that lets Next.js **App Router** API routes be written in
NestJS style: decorator-based controllers (`@Controller`, `@Get`/`@Post`/`@Put`/`@Patch`/
`@Delete`/`@Head`/`@Options`), `@Body(DtoClass)` request validation via `class-validator`,
`@AuthGuard`/`@CurrentUser` route protection, `@Use` middleware, and OpenAPI/Swagger doc
generation from the same decorators. It is **routing + validation + auth guard + docs
only** — deliberately no DI container, no modules, no pipes, and `@AuthGuard` is a single
global-resolver mechanism, not a pluggable Nest-style guard *class* system. Legacy TS
decorators (`experimentalDecorators`/`emitDecoratorMetadata`), no `reflect-metadata`.

Origin: the decorator/validation pattern was ported from a sibling project,
`school-management-system` (`/Users/mac/Desktop/dev/school-management-system`), where it was
already proven in production. When in doubt about "how should X behave," that project is the
reference implementation to check against.

## Commands

- `npm run build` — `rm -rf dist && tsup && chmod +x dist/cli.js`. Two parallel tsup configs
  (library entry + CLI entry) in `tsup.config.ts`; both have `clean:false` (only the npm
  script does the `rm -rf`, to avoid the two configs racing and wiping each other's output).
  The CLI config deliberately has **no** `esbuildOptions.drop` — dropping `console.*` would
  silently kill all CLI output.
- `npm run dev` — `ts-node ./src/index.ts` (source, not built).
- `npm run test` — `npm run build && npm link` (there is no unit test suite; "testing" this
  library means building it, linking/packing it into `example/`, and exercising real routes
  against a real `next dev` server — see "How to verify a change" below).

## Architecture notes

### Parameter decorators (`param-registry.ts`)

SWC/esbuild don't reliably apply parameter-decorator prototype mutations the way `tsc` does,
so parameter decorators (like `@Body`) don't mutate the class directly. Instead:
`registerParam(target, propertyKey, parameterIndex, resolver)` stores a resolver function in
a registry keyed by class+method+index. `@Controller` (via `wireParamResolvers`) reads that
registry at class-decoration time and rewires each decorated method to run all its
parameter resolvers before calling the original method. This indirection is required — don't
"simplify" it into a direct parameter-decorator mutation without checking it survives an
esbuild/SWC build, not just `tsc`.

`param-registry.ts` also exports `isRouteContext()` — the duck-type check that tells apart
"called as a route handler" (has `request`/`params`/`query` and a `.json()` method) from
"called directly as a Server Action" (anything else). It's shared by `@Body` and
`@CurrentUser`, the two decorators that need to behave differently depending on which shape
they're fed — it used to be defined separately, verbatim, in both `body.ts` and
`current-user.ts`; consolidated here since both already import from this module. If a third
decorator needs the same distinction, import it from here rather than re-defining it again.

### Body validation, and why it also works as a Server Action (`body.ts`)

`@Body(DtoClass)` duck-types its raw input via `isRouteContext()` (above): if it looks like
a `RouteContext`, it reads the JSON body from the request.
Otherwise it treats the argument itself as the raw payload. This means a
`@Body`-decorated controller method works two ways with **zero extra code**:

1. Normal API route, dispatched by the catch-all route through `createApplication`.
2. Bound directly and exported as a Next.js **Server Action**
   (`export const createX = controller.create.bind(controller)`), called with a plain
   object. Validation runs identically; failures return the same
   `{ success: false, message, errors }` shape instead of throwing.

This dual-mode behavior — "action validation" in the user's own terms — is documented in
README.md ("Server Action validation") and in the docs site
(`docs/core-concepts/dto-validation.md`, same heading). It was verified working via a
direct smoke test against the built `dist/` output (bypass `createApplication` entirely,
call the decorated method with a plain object, confirm the validation-failure shape).

File/`FileList` fields are stripped out before `plainToInstance` runs and reattached
untouched afterward — `class-transformer` otherwise crashes trying to construct a `File`
from scratch via `value.constructor`.

### Auth guard (`decorators/auth-guard.ts`, `decorators/current-user.ts`, `utils/auth.ts`)

Ported from `school-management-system`'s `@AuthGuard(['ADMIN'])`/`@CurrentUser()`, but
**deliberately re-architected**, not copied as-is — the source implementation had three
real problems this port fixes:

1. Source `AuthGuard` mutated `descriptor.value` directly, its own third dispatch mechanism
   alongside `@Use`'s middleware chain and the param-registry. This port instead makes
   `AuthGuard(roles?)` **sugar over `Use(...)`** (`Use(async (context, next) => {...})`,
   returned directly) — no new mechanism, and it correctly runs *before*
   `wireParamResolvers`' param resolution, since `@Use` middlewares wrap the whole handler
   call in `register.ts`, not just the handler body.
2. Source `AuthGuard`/`CurrentUser` never shared state — each independently re-ran the
   resolver (re-read headers, re-hit the DB) on every request that had both. This port's
   `resolveCurrentUser()` (`utils/auth.ts`) caches the resolved user on the `RouteContext`
   object itself (a plain property, not exported/public) so `@CurrentUser()` reuses
   `@AuthGuard()`'s resolution on the same request instead of resolving twice.
3. Source's failure responses had no real HTTP status (everything came back 200 — same bug
   class already fixed for `Response.XXX()` generally, see below). This port's `AuthGuard`
   returns `Response.Unauthorized()`/`Response.Forbidden()`, which now carry real
   `statusCode` (401/403) per the fix below.

There's no bundled JWT/session logic and no database dependency — the source project's
`resolveAuthUser()` was tightly coupled to `next/headers` + Drizzle + a specific cookie/env-var
quirk (`process.env.JWT_SECRET` doubling as both signing secret *and* cookie name) that isn't
appropriate to bake into a generic library. Instead there's one consumer-supplied hook:
`configureAuth({ resolveUser })`, called once (e.g. in `app.ts`). `resolveUser` receives the
`RouteContext` and returns `TUser | null` — token format, header/cookie choice, `verify()` vs
`decode()`, and the user shape are entirely up to the consumer. If `configureAuth` was never
called, `resolveCurrentUser()` throws (not a silent `null`) — misconfiguration should fail
loud, not quietly let every route return 401.

Verified end-to-end via a smoke test hitting real routes through `createApplication`'s
dispatcher (not just calling the decorator function directly): no token → 401, wrong role →
403, correct role → 200 with `@CurrentUser()` correctly injecting the resolved user object.

### `Response` helper and HTTP status codes (`utils/Response.ts`)

`Response.XXX()` methods return plain objects carrying a visible `statusCode` field (same
convention NestJS's own exception bodies use) — deliberately **not** `NextResponse`
instances and **not** a hidden/Symbol-keyed status, because the same object also has to work
when returned directly from a bound Server Action (see "Body validation" above), where
there's no HTTP response to attach a status to and only plain serializable data survives.

The three response-dispatch sites — `register.ts`'s `executeController` and
`createApplication.ts`'s `executeHandler` and its final composed-middleware fallback — all
call `buildRouteResponse(context, result)` (exported from `Response.ts`) before returning a
non-`Response` handler result. That function reads `result.statusCode` (if present and
numeric) into a `ResponseInit`, so `return Response.NotFound()` from a handler produces a
real HTTP 404, not a 200 with an error-shaped body. **Before this existed, every
`Response.XXX()` return was silently served as HTTP 200** (a real bug, caught and fixed when
the method set was expanded). If you add a new `Response.XXX()` method, give it a
`statusCode` field or it will silently serve as 200.

`buildRouteResponse` also special-cases `204`/`205`/`304` (`NO_BODY_STATUSES`): the Fetch
spec's `Response` constructor throws "Invalid response status code" if you attempt a body
on those statuses, so `Response.NoContent()` (204) would crash `NextResponse.json(...)` if
passed through the normal path — caught by the end-to-end route-dispatch smoke test, not by
the build or a unit-level check. **Don't call `context.json(result, init)`/`NextResponse.json`
directly at a dispatch site** — always go through `buildRouteResponse`, or a future no-body
status will reintroduce this crash.

Full method set: `Ok`/`Created`/`NoContent` (2xx), `BadRequest`/`ValidationFailed`/
`Unauthorized`/`Forbidden`/`NotFound`/`Conflict`/`TooManyRequests`/`InternalServerError`
(4xx/5xx), plus the pre-existing `BadPage`/`EmptyPage` pagination shapes. Documented in
README.md ("`Response` helper" under API reference) and
`docs/core-concepts/handler-return-values.md` in the doc site — keep both in sync with the
method list here.

### Swagger UI (`openapi/swagger-ui.ts`)

Swagger UI assets are **not vendored** — `createSwaggerUiHandler()` does
`await import("swagger-ui-dist")` (not `require()`) and serves the consumer's own installed
copy. `import()` instead of `require()` is required for Turbopack compatibility (Turbopack's
static external-package analysis can't see through esbuild's ESM `require()` shim, even with
`serverExternalPackages` configured — this cost real debugging time, don't revert it).
Because `import()` needs type info that untyped `require()` didn't, there's an ambient
declaration at `src/types/swagger-ui-dist.d.ts`.

The served HTML injects `<base href="{pathname-without-trailing-slash}/" />` — without it,
relative asset URLs (`swagger-ui.css` etc.) resolve one level too shallow whenever the
request URL lacks a trailing slash.

### Route matching (`createApplication.ts`'s `matchRoute`)

`handle()` walks `this.routes` once per request and calls `matchRoute()` at most once per
candidate, capturing the winning route's params on the same pass — it used to call
`.find()` to locate the route and then call `matchRoute()` again on the winner to get its
params, running the same segment-split-and-compare work twice for every matched request.
Keep this a single pass if you touch it again.

Pure declaration-order, first-match-wins — no static-vs-dynamic
segment prioritization (same as Express). A literal route colliding with an earlier dynamic
one (e.g. `@Get("/:id")` declared before `@Get("/search")` on the same controller) will
never be reached; `:id` matches first. This surfaced as a real test-authoring mistake while
writing the end-to-end smoke test for this repo (a `/hello/with-mw` route was silently
swallowed by an earlier `/hello/:id`) — not a library bug, but a sharp edge worth remembering
when adding routes to any test/example controller: declare specific/literal paths before
colliding param paths on the same controller.

### Middleware composition (`utils/compose.ts`)

`composeMiddlewares(context, middlewares, execute)` is the one place that reduceRight-wraps
a list of middlewares around a base executor — shared by `register.ts` (per-route
`@Use`/`@AuthGuard`) and `createApplication.ts` (app-level `app.use()`), which used to
implement the same ~10-line composition independently. **The base `execute` is still the
only thing responsible for turning its own result into a real response** (via
`buildRouteResponse`, not something `composeMiddlewares` does) — this matters because a
middleware can short-circuit by returning a plain object directly (e.g. `AuthGuard` doing
`return Response.Unauthorized()` without calling `next()`) instead of a finalized
`NextResponse`. That plain object bubbles up through the compose chain untouched; it's
`register.ts`'s `handler` returning it to `createApplication.ts`'s `executeHandler`, and
*that* layer's own `instanceof Response` / `buildRouteResponse` check that actually finalizes
it — not the route-level layer where the middleware live. Don't "fix" this by adding a
finalize step to `composeMiddlewares` itself; it's already covered one layer up, and a
middleware doing `const response = await next(); response.headers.set(...)` (see the CORS/
timing examples in the README) depends on `next()` already resolving to a real `NextResponse`
when it comes from the base executor, not from `composeMiddlewares` finalizing late.

### Peer dependencies

`class-validator`, `class-transformer`, `class-validator-jsonschema`, `swagger-ui-dist` are
`peerDependencies` with `peerDependenciesMeta.optional: true` (not hard `dependencies`) —
deliberate choice so consumers who only need routing/middleware aren't forced to install
validation/docs tooling they don't use. Keep this split when adding new optional integrations.

### Public API surface (`index.ts`)

The barrel intentionally exports **only** what's documented in README.md's API reference —
no low-level registries/plumbing (`controllerRegistry`, `routeRegistry`, `registerParam`,
`wireParamResolvers`, `apiTagsRegistry`, `apiOperationRegistry`, `apiResponseRegistry`,
`bodyDtoRegistry`, `registerBodyDto` were all trimmed from the barrel in an audit pass —
none of them were used anywhere outside their own module via relative imports, so removing
them from `index.ts` was a pure surface reduction, not a behavior change; each module still
imports what it needs directly from its sibling file). If you add a new decorator that needs
cross-module registry access (the way `@Body`/`@AuthGuard`/`@CurrentUser` do), wire it via a
direct relative import first — only add something to `index.ts` once there's a real,
documented reason for a consumer to import it. The library isn't published yet (unlisted on
npm as of this writing), so barrel changes are still free; that won't be true after the
first release — removing something from `index.ts` post-publish is a breaking change.

## How to verify a change

There's no automated test suite. To validate a change end-to-end:

1. `npm run build`
2. Pack it (`npm pack`) into a content-hash-suffixed tarball filename and install that into
   `example/` — **do not reuse the same tarball filename across installs**; Yarn Classic's
   `file:` dependency cache has repeatedly served stale content for a reused filename even
   after `rm -rf node_modules yarn.lock`. If you hit inexplicable stale-code symptoms after a
   reinstall, suspect `~/Library/Caches/Yarn/v6/npm-<pkg>-<version>-<hash>` before anything
   else.
2b. For a quick isolated check that doesn't need the full example app (e.g. verifying a
    decorator behaves correctly outside a route), a throwaway `ts-node` script run against
    `./dist/index.js` with `experimentalDecorators` compiler options works and is faster —
    see the "Body validation" verification above for the pattern. Delete the scratch file
    afterward.
3. Run `next dev` (Turbopack) inside `example/` and hit the real routes — this is the only
   way earlier Turbopack-specific bugs (the `swagger-ui-dist` `require()` issue) were caught;
   `tsc`/build success alone does not guarantee Turbopack compatibility.

## Known gotchas (already fixed once, don't reintroduce)

- `tsconfig.json`: `experimentalDecorators`/`emitDecoratorMetadata` must be **inside**
  `compilerOptions`, not siblings of it.
- `tsconfig.json`: `lib` must include `"DOM","DOM.Iterable"` or `FileList`/`Request.json()`
  types break.
- `package.json` `files`/READMEs are case-sensitive on publish — the canonical filename is
  `README.md` (was once `readme.md`, broke on case-sensitive machines).
- CLI's `relativeImport()` path-diffing: diff `dirname(to)` vs `dirname(from)` and reattach
  `basename(to)` separately — don't `path.relative()` the full paths directly when a file and
  a same-named sibling directory (`src/app.ts` vs `src/app/`) are both in play.
- CLI's `generate controller` array-splicing into `controllers: []`: never build the
  replacement via a nested `.replace(innerMatch, newValue)` when `innerMatch` can be an empty
  string — `"".replace("", x)` inserts at position 0 of the *whole* string, not where you
  think. Reconstruct the full matched substring directly instead.
- CLI's `printResults()` (`cli.ts`) only ever receives `"written" | "skipped"` from
  `writeFileSafe()` — a third `"registered"` status it checked for came from a *different*
  return value (`tryRegisterController`'s own result, already handled separately by `main()`)
  and could never actually appear in `results`. Caught in a dead-code audit; don't
  reintroduce a branch for a status `results` items can't carry — check what a function
  actually returns before adding a case for it.
- `Response.NoContent()` (and any future `Response.XXX()` using 204/205/304): the Fetch
  spec's `Response` constructor throws if you attempt a body on these statuses.
  `buildRouteResponse()` (`utils/Response.ts`) special-cases them — go through it, don't call
  `context.json()`/`NextResponse.json()` directly at a dispatch site (see the `Response`
  helper section above; this was a real crash caught by the end-to-end route-dispatch smoke
  test, not by the build).
